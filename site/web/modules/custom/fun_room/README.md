# Fun room

Rooms and participants for the Fun-o-Meter. Attendees join a room with a code;
the Join component (`fun-canvas-project`, and the standalone `prototype/`) talks
to this module through core JSON:API, and every room has a page rendered by one
Canvas template.

## What it provides

- **Room** is a node of type `room`. The title is the room code (stored trimmed
  and uppercase, and unique among rooms). Fields: `field_status` (`open` or
  `closed`), `field_current_slide` (zero-based index),
  `field_current_slide_id` and `field_current_slide_title`. Pathauto serves each room at `/room/<code>`, for
  example `/room/ned-4261`. Rooms are not content-moderated; a room is just open
  or closed.
- **Participant** (`fun_participant`, a custom entity): `room` (reference to a
  room node), `name` (1-30 characters), `avatar` (0-5) and a write-only `token`.
  Only the token's SHA-256 is stored (`token_hash`); the secret is generated by
  the client and never readable. It also holds the attendee's current fun level
  (`fun`, 0-100, empty until they first move the slider) and when it changed
  (`fun_at`). Neither can be set through JSON:API, only through the vote endpoint.
- **Vote** (`fun_vote`, a custom entity): one attendee's fun level on one slide,
  with `participant`, `room`, `slide` (the room's zero-based slide index when they
  voted), `value` and timestamps. At most one row per participant per slide: moving
  the slider again on the same slide updates that row, and the next slide starts a
  new one. These rows are the history the end-of-session recap is built from.
- **Access:** anyone can read published rooms and create a participant (the
  `join fun room` permission, granted to anonymous and authenticated users on
  install). Everything else, including reading participants, needs
  `administer fun_room`; creating or editing rooms is ordinary node access.
- **Rate limit:** 50 joins per 5 minutes per IP, then HTTP 429.
- **On install** the module enables JSON:API writes (`jsonapi.settings:
  read_only: false`; core ships JSON:API read-only) and takes `room` out of
  Drupal CMS's editorial workflow, which would otherwise keep every new room an
  unpublished draft (a 404 for attendees).
- All of the module's config is marked as enforced by the module, so Drupal can
  remove it with the module. (Uninstalling is not covered by the tests.)

## Local setup

From `site/`, with DDEV running:

```bash
ddev drush en fun_room -y
ddev drush fun-room:create NED-4261
```

### CORS for local clients (not in git)

Canvas pages served by Drupal are same-origin and need nothing. The standalone
prototype, the slide deck and Canvas Workbench run on other localhost ports, so
the browser blocks their calls unless Drupal allows those origins.

Create `site/web/sites/default/services.yml` (it is gitignored by
`site/.gitignore`, so a fresh checkout must recreate it):

```yaml
parameters:
  cors.config:
    enabled: true
    allowedHeaders: ['Content-Type', 'Accept', 'Authorization', 'X-Presenter-Key', 'X-Participant-Token']
    allowedMethods: ['GET', 'POST', 'OPTIONS']
    allowedOrigins: []
    allowedOriginsPatterns: ['#^http://localhost:\d+$#', '#^http://127\.0\.0\.1:\d+$#']
    exposedHeaders: false
    maxAge: false
    supportsCredentials: false
```

Then `ddev drush cr`. If the file already exists, merge the `cors.config` block
into it. Drupal only loads `services.yml`, not `default.services.yml`. CORS
applies to the whole site, not just `/jsonapi`. Production origins are a deploy
decision, so do not copy these localhost patterns there.

Check it from a terminal (expect `access-control-allow-origin` in the output):

```bash
curl -sk -i -X OPTIONS https://fun-canvas-code.ddev.site/jsonapi/fun_participant/fun_participant \
  -H 'Origin: http://localhost:5173' -H 'Access-Control-Request-Method: POST' \
  | grep -i access-control
```

## API

Look up a room by code (an empty `data` array means no such room). The response
includes `field_status`, `field_current_slide` and `path.alias`:

```bash
curl -sk -g 'https://fun-canvas-code.ddev.site/jsonapi/node/room?filter[title]=NED-4261' \
  -H 'Accept: application/vnd.api+json'
```

Read one room by its JSON:API id (this is what the room page polls):
`GET /jsonapi/node/room/{uuid}`.

Join: `POST /jsonapi/fun_participant/fun_participant` with
`Content-Type: application/vnd.api+json`. The `token` must be 16-128 characters
and `relationships.room` is the room's JSON:API `id` from the lookup above:

```json
{
  "data": {
    "type": "fun_participant--fun_participant",
    "attributes": { "name": "Sam", "avatar": 2, "token": "<secret, 16-128 chars>" },
    "relationships": {
      "room": { "data": { "type": "node--room", "id": "<room uuid>" } }
    }
  }
}
```

| Result | Meaning |
|---|---|
| 201 | Joined. The response never includes the token. |
| 422 | Invalid name, avatar or token, or the room is closed (pointer `/data/attributes/room`). |
| 403 | Not allowed, for example reading or changing a participant anonymously, or creating a room. |
| 429 | Too many joins from this IP. |

## Presenter endpoint (live slide number)

The slide deck tells a room which slide is showing, and the room page picks it up
by polling. The deck runs in the presenter's browser, so there is no login; the
request carries a shared secret instead.

`POST /api/fun/rooms/{code}/slide` with `Content-Type: application/json` and the
header `X-Presenter-Key: <key>`:

```bash
curl -sk -X POST https://fun-canvas-code.ddev.site/api/fun/rooms/NED-4261/slide \
  -H 'Content-Type: application/json' -H "X-Presenter-Key: $KEY" \
  -d '{"index": 4, "id": "swarm", "title": "Live demo: the Swarm"}'
```

`index` is the zero-based slide index (an integer, 0-999) and is required. `id` is
the optional stable slide id (lowercase letters, digits, `-` and `_`, up to 64
characters). `title` is the optional slide title shown in the room page's "Now
showing" bar: plain text of at most 255 characters, with runs of whitespace
collapsed to one space and no control characters. A report replaces all three, so
leaving `id` or `title` out clears it. The code is matched case-insensitively, and
a closed room can still be updated.

| Result | Meaning |
|---|---|
| 200 | Updated; returns `{code, index, id, title}`. |
| 400 | The body is not a JSON object. |
| 403 | Missing or wrong key. |
| 404 | No such room. |
| 422 | Invalid `index`, `id` or `title`. |
| 429 | Too many wrong keys from this IP (30 per 5 minutes). The correct key is never rate-limited. |
| 503 | No presenter key is configured, so nothing can be changed. |

### Setting the key

The key is read from `$settings['fun_room_presenter_key']` if that is set (even to
an empty string, which disables the endpoint), otherwise from the
`FUN_ROOM_PRESENTER_KEY` environment variable. For local DDEV, add it to the
git-ignored `site/.ddev/config.local.yaml` and `ddev restart`:

```yaml
web_environment:
  - FUN_ROOM_PRESENTER_KEY=<a long random string, e.g. from `openssl rand -hex 32`>
```

Use the same value as `VITE_PRESENTER_KEY` in the deck's `slides/.env.local`. The
deck is a different origin from the site, so its request needs a CORS preflight to
pass: add `'X-Presenter-Key'` to `allowedHeaders` in `services.yml` (see "CORS for
local clients" above).

## The swarm and the slider

The slider sends each attendee's fun level, and the swarm shows everyone's.
Attendees are not logged in: voting needs the secret the attendee made when they
joined, matched to their participant by its hash.

`GET /api/fun/rooms/{code}/state` is public and read-only, and works for a closed
room too (the final picture). It returns:

```json
{
  "code": "NED-4261", "status": "open", "slide": 4,
  "count": 37, "voters": 31, "median": 64, "tier": "mid",
  "dots": [{ "id": "a1b2c3d4e5f6", "x": 72, "y": 31.4, "avatar": 2 }],
  "updated": 1794176859
}
```

`count` is everyone who joined; `voters` and `dots` are those who have moved their
slider. `median` is the middle value (for an even count, the rounded average) and
`tier` is `low` below 35, `mid` below 65, otherwise `high`; both are `null` with no
voters. Each dot has an opaque, stable `id` and a vertical place `y` (8 to 92)
derived from it, so dots keep their place between polls. It never contains names,
tokens or uuids. The result is reused for 1 second per room.

`POST /api/fun/rooms/{code}/vote` with `Content-Type: application/json`, the header
`X-Participant-Token: <the attendee's secret>` and a body of `{"value": 70}`:

| Result | Meaning |
|---|---|
| 200 | Recorded; returns `{id, value, slide}`. `id` is the attendee's own dot in the swarm. |
| 400 | The body is not a JSON object. |
| 403 | Missing or wrong token, or a token from another room. |
| 404 | No such room. |
| 409 | The room is closed; the fun is over. |
| 422 | `value` is not a whole number from 0 to 100. |
| 429 | Too many votes (20 per participant per 10 seconds, or 3000 per IP per minute). |
| 503 | The vote could not be recorded right now; try again. |

Load: with N attendees polling every 2 seconds the swarm gets about N/2 requests a
second, and the 1-second reuse means the database is queried at most once a second
per room. Lengthen the swarm's `pollMs` if a server struggles.

The room page's slider and swarm are the `fun-slider` and `swarm` Canvas components,
placed in the room template. For Canvas Workbench (a different origin from the site),
add `'X-Participant-Token'` to `allowedHeaders` in `services.yml`, as in the CORS
snippet above.

### Comments

Attendees post short comments from the room page; they show there and in the deck's
activity stream, tagged with the slide that was showing. Comments are `fun_comment`
entities (`participant`, `room`, `slide`, `slide_title`, `body`, `created`), admin-only
and written only by the endpoint below (never through JSON:API).

`GET /api/fun/rooms/{code}/comments?after={id}&limit={n}` is public and read-only, works
for closed rooms, and returns `{comments: [{id, name, avatar, slide, slideTitle, text,
at}]}` oldest first. Without `after` it returns the newest `limit` (default 30, at most
50); with `after` only comments with a higher id, so a poller asks for just what is new.
It is cached for a second. Names and avatars are the ones attendees chose when joining,
so they are public to anyone who loads the room. No token, uuid or participant id is returned.

`POST /api/fun/rooms/{code}/comments` with `{"text": "..."}` and `X-Participant-Token`:

| Status | Meaning |
|---|---|
| 201 | Saved; the body is the comment as the feed shows it. |
| 400 | The body wasn't valid JSON (this includes text that isn't valid UTF-8). |
| 403 | Missing or unknown token, or a token from another room. |
| 404 | Unknown room. |
| 409 | The room is closed. |
| 422 | `empty` (nothing left after cleaning), `too_long` (over 280 characters) or `invalid_text` (not a string). |
| 429 | Too many comments (5 per participant per minute, or 600 per IP per minute). |

The text is cleaned before it is stored: control characters become spaces, invisible
format characters (zero-width, right-to-left overrides) are dropped, whitespace is
collapsed. It is plain text, so clients must render it as text. An identical comment from
the same attendee within 30 seconds returns the original instead of adding a copy.

There is no moderation UI. To remove a comment, find its id (it is in the feed) and run
`ddev drush entity:delete fun_comment <id>`; it disappears from the room page and the deck
within a couple of seconds. The room page's `comments` component and the deck's
`ActivityStream` both poll this endpoint (about every 3 and 2 seconds), served mostly from
the one-second cache.

### Requests

Attendees ask for a party hat, a noise maker or candy from the room page, with an optional
note about where they are sitting. A request stays **open** until a volunteer marks it
**delivered** (or the attendee **cancels** it); then they can ask again. Requests are
`fun_request` entities (`participant`, `room`, `kind` = `hat`/`noise`/`candy`, `note` up to
40 characters, `slide`, `status`, `created`, `changed`), admin-only and written only by these
endpoints. Each attendee can have one open request per kind: asking again while one is open
returns the existing one (200) instead of adding a copy.

| Endpoint | Auth | Notes |
|---|---|---|
| `GET /api/fun/rooms/{code}/requests?since={unix}&limit={n}&ids={a,b,c}` | public | `{requests: [{id, name, avatar, kind, note, slide, status, at, changed}]}`, oldest change first. Without `since`: the newest `limit` (default 30, max 50) that are not cancelled. With `since`: everything changed at or after it, **including cancelled** ones so clients can drop them. With `ids` (up to 20): exactly those, whatever their status. Cached a second; works for closed rooms. |
| `POST .../requests` `{kind, note?}` | `X-Participant-Token` | 201 new, 200 the existing open one; 400 bad JSON; 403 bad token; 404 unknown room; 409 closed; 422 `invalid_kind` / `invalid_note` / `too_long`; 429 over 6 a minute per attendee (or 600 per IP). |
| `POST .../requests/{id}/cancel` | `X-Participant-Token` | Only the attendee's own open request (403 for someone else's); anything not open is returned unchanged. |
| `POST .../requests/{id}/deliver` | `X-Presenter-Key` | Marks it delivered (idempotent); works in a closed room; 404 if the id isn't in this room. |

The cursor is the change time rather than the id, because a request keeps its id when it is
delivered or cancelled. Delivering uses the same shared secret as slide reports, through one
service (`fun_room.presenter_key`, `PresenterKeyChecker`): 503 if no key is configured, wrong
keys counted and limited per IP, the right key never limited. From the terminal,
`ddev drush fun-room:deliver <id>` does the same as the Delivered button. Names and notes
are public (on the deck and in the feed); an unwanted request can be removed with
`ddev drush entity:delete fun_request <id>`.

### Rating events

The deck's activity stream also shows each attendee's slide ratings (their `fun_vote` rows).
`GET /api/fun/rooms/{code}/ratings?since={unix time}&limit={n}` is public and read-only,
works for closed rooms, is cached for a second, and returns `{ratings: [{id, name, avatar,
slide, value, tier, at, changed}]}` oldest change first. There is one entry per attendee
per slide (`id` is the vote's id, `slide` is zero-based, `tier` is `low`/`mid`/`high` from
the same thresholds as the swarm). Because a vote keeps its id when its value changes, the
cursor is the change time: `since` returns votes changed at or after that second, and the
client updates by `id`. Without `since` you get the newest `limit` (default 30, at most 50);
if more than `limit` changed, the newest `limit` are returned.

A vote is listed only once it has been unchanged for 3 seconds, so someone dragging their
slider appears once with the value where they stopped. Names go with values here: ratings
are public by name on the deck and in this feed (the swarm itself stays anonymous). No
token, uuid or participant id is returned.

### Recap

`GET /api/fun/rooms/{code}/recap` is the end-of-session summary, shown by the room page (the
`recap` component, which replaces the swarm once the room is closed) and the deck (the recap
view, `D`). Public and read-only. It is computed on read, so nothing happens when a room
closes; an open room returns a recap too (with `"status": "open"`, so the presenter can rehearse).
It is cached for 5 seconds while the room is open and 5 minutes once it is closed. Returns:
`code`, `status`, `headline` (from the tier), `attendees`, `voters`, `durationSeconds`
(first slide the deck reported to the last vote, comment or request; null if unknown),
`averageFun` (the median of every rating, null if none) and `tier`, `peak`, `timeline` (slides in
slide order), `topSlides` (best five), `quietest`, `comments {count, busiest}`, `requests {total,
hat, noise, candy, delivered}` (cancelled ones excluded), `highlights` and `updated`. A slide is
`{slide, title, median, votes}` (`slide` is zero-based).

Ratings are one row per attendee per slide (the last value), so the timeline is **by slide**, not
by minute. Every rated slide is charted. To be ranked (peak, top slides, quietest) a slide needs at least 2 ratings (`RoomRecap::MIN_VOTES`), except in rooms with fewer than 5 voters (`RoomRecap::SMALL_ROOM`), where any rated slide is ranked.
Highlights are picked by rule, not by judging what was funny: a comment from the slide with the
most comments, the final comment, and the most asked-for request kind. No token, uuid or
participant id is returned; names and avatars are only the ones comments already show.

Votes know only their slide's index, so slide titles come from the **slide log**: the
`field_slide_log` JSON on the room, written by the slide endpoint each time the deck reports a
slide (index, id, title and the first time it was shown; at most 200). A slide the deck never
reported is named from a comment's slide title, else "Slide N". Rooms run before the log existed
get "Slide N" labels. Reordering the deck mid-event would mislabel slides.

### Mood theming

The server's `tier` (`low` below 35, `mid` below 65, else `high`, none with no votes)
themes the whole room page. The `swarm` component writes the tier to
`<html data-mood="waiting|low|mid|high">` and `src/global.css` turns it into colors
(`--mood-bg`, `--mood-field`, `--mood-accent`, used as `bg-mood-bg` and so on). To
stop a median sitting on a threshold from flickering, a new tier is shown only after
two polls in a row report it (`createSteadier` in `fun-room-mood.ts`). When the room
climbs into `high` from `low` or `mid`, confetti goes off once (not on a reload into
`high`, and at most once a minute). Both the fade and the confetti are off for people
who ask for reduced motion. Add `?mood=low|mid|high|waiting` to the room page's address
to preview a mood without votes. The deck does the same from its own poll (`slides/src/mood.js`).
Thresholds live only in `SwarmState`; the colors must keep dark ink readable (4.5:1).

## Managing rooms

Rooms are ordinary content. In the admin sidebar use **Create > Room** to add
one, or **Fun rooms** (the Content list filtered to rooms) to see them. Set
**Status** to Closed to stop new joins, ratings, comments and requests; the room page then shows
the recap and the deck gets a Recap button. **Fun participants** lists who joined, newest first. Deleting a room
does not delete its participants.

From the command line (both accept any case; the code is stored uppercase):

```bash
ddev drush fun-room:create NED-4261   # create, or reopen if it exists; prints the room path
ddev drush fun-room:close NED-4261
```

Use a new code for each event; there is no "reset room" action.

## Room page (one Canvas template for every room)

Canvas content templates only support nodes in Canvas 1.12, which is why rooms
are nodes. `fun-canvas-project/content-templates/node.room.full.json` is the
single template: it renders every room node with the `room` component (code,
open/closed status, current slide, polled every 2 seconds) and a `placeholder`
in each of its four slots (`swarm`, `slider`, `requests`, `comments`). When a
feature's backend lands, build its component and replace that slot's placeholder
in the template; `room` does not change.

From `fun-canvas-project/`:

```bash
npm run canvas -- validate
npm run canvas -- push --no-pages --no-page-templates --no-include-brand-kit -y
```

The template is enabled by the push. A visitor who has not joined that room in
this browser sees a "Join this room" link to `/?code=<code>`; the home page's
Join component sends anyone who has joined straight to their room.

Functional tests use `drupal/core-dev`. From `site/`:

```bash
ddev exec 'mkdir -p /tmp/bto && SIMPLETEST_BASE_URL=http://localhost SIMPLETEST_DB=mysql://db:db@db/db BROWSERTEST_OUTPUT_DIRECTORY=/tmp/bto vendor/bin/phpunit -c web/core web/modules/custom/fun_room'
```
